### 1. Wireshark 过滤与导出

```text

frame.number == 152 || frame.number == 153

```

先在 HTTP 请求中定位目标文件，再检查第 153 帧响应。提取的是 HTTP 响应体原始字节，不是完整响应报文，也不是 Wireshark 文本或十六进制截图。已保存的响应体为 frame153-response.bin。

### 2. 文件头推导单字节 XOR

| 内容          | 前四个字节       |
| ----------- | ----------- |
| 原响应体        | 29 32 7a 7d |
| ZIP 常见本地文件头 | 50 4b 03 04 |
| 逐字节 XOR 差值  | 79 79 79 79 |

```text
0x29 ^ 0x50 = 0x79
0x32 ^ 0x4b = 0x79
0x7a ^ 0x03 = 0x79
0x7d ^ 0x04 = 0x79
```

四个位置的差值一致，提示整段响应体可能与 0x79 进行了单字节异或。应用于全部 371 字节后，可正常解析为 ZIP；ZIP 的 CRC 校验通过。

> 以上表格依据 http-evidence.json 与响应体字节生成，是分析证据表。此次没有采集 Wireshark 原生窗口截图。

### 3. ZIP、JWT 与签名验证

### 签名校验：不是 HS256

头部算法名为 HS-SM3。本地已有候选搜索结果；本次再次用 HMAC-SM3 核验。签名输入是未经改写的 header.payload 两段编码文本，而不是重新序列化的 JSON。将计算结果与第三段 Base64URL 解码后的 32 字节签名比较，结果完全一致。

```text
已核验签名密钥：
your_secret_value_dont_share_this

HMAC-SM3(header.payload, key) == signature
结果：True
```

此前候选来源为公开 JWT secrets 字典，本地文件有 103,979 行。候选命中并经签名逐字节匹配，说明该密钥可验证这枚 JWT；不代表已确认比赛平台要求提交它。

### 口令边界与 ZIP 验证

已完成阶段止于解密压缩包并读取截获信息

### 1. 可复现的提取代码

```python
from PIL import Image
img = Image.open("附件1-图片.png").convert("RGB")
bits = []
for pixel in img.getdata():
    bits.extend(channel & 1 for channel in pixel)
    if len(bits) >= 256:
        break
data = bytes(
    sum(bits[i+j] << (7-j) for j in range(8))
    for i in range(0, 256, 8)
)
print(repr(data))
```

### 2. 提取出来的可打印前缀不等于密码长度

```text
提取字节前缀：S3cr4t_P4SsW0rDIf ...
正确口令：    S3cr4t_P4SsW0rD
正确口令长度：15 字符
```

隐写文本后面继续读取的是载体数据，其中偶然出现可打印字符 If。用 17 字符候选解压失败；用前 15 字符口令可成功读取 ZIP 全部内容，内容 CRC32 与归档记录一致。这是确定密码边界的依据。

| 核验项               | 结果                               |
| ----------------- | -------------------------------- |
| S3cr4t_P4SsW0rDIf | Bad password，失败                  |
| S3cr4t_P4SsW0rD   | 成功                               |
| 解出文件              | 截获信息.txt（归档未标 UTF-8，文件名按 GBK 解释） |
| 文件大小 / CRC32      | 630 字节 / 03ed0cf3                |

### 3. ZIP 内内容与下一阶段

文件给出 MSG1、MAC1、MSG2、MAC2，要求伪造一个新消息：总长 48 字节；最后 16 字节与 MSG2 的最后 16 字节一致；认证结果仍为 MAC2。

> 停止点：口令、归档解密、CRC 及内部任务文字已验证。本文不构造伪造消息，不声称已有新 MAC 或最终 flag。已解出的任务文字另存于验证记录/紧急援助-截获信息.txt。

## 4. 密径寻钥：Wiener 与 PNG 高度恢复

已完成：由公开 n、e 恢复 d，并得到 key1

附件3：key1-RSA-cry.py 在生成私钥时先选 d，再算 e。关键条件如下。n、e、c 已由附件4给出，解题者不需要重新生成这三个值。

```python
d = random.getrandbits(1024 // 4)
if gcd(d, phi_n) == 1 and 36 * d**4 < n:
    break
e = invmod(d, phi_n)
c = pow(m, e, n)
```

该条件强制 d 相对 n 较小。Wiener 利用 ed - k·φ(n) = 1 及 φ(n) 与 n 的接近关系，把 e/n 的连分数收敛分数 k/d 当成候选。逐个候选推导 φ(n)，检查 p、q 是否为整数且 p·q = n。经典充分条件还涉及两个素数大小接近；本题最终以整数因子校验确认命中。

## 5. 复现中容易踩的坑

| 场景           | 容易出错的地方                               | 本文采用的判断依据                                  |
| ------------ | ------------------------------------- | ------------------------------------------ |
| JSFuck 与中文编码 | 把编码器源码当密文，或用 UTF-8 读取 GBK 字节          | 先确认真正的表达式文件，再核对解码后字节与中文提示                  |
| HTTP 文件还原    | 导出完整响应报文，或把十六进制显示文本当原始字节              | 使用响应体原始数据，恢复后检查 ZIP 结构与 CRC                |
| JWT 签名       | 忽略 `HS-SM3`，或重新序列化 JSON 后计算签名         | 使用原始 `header.payload` 字符串做 HMAC-SM3 校验     |
| LSB 文本提取     | 只看黑白位平面，或者把末尾偶然可打印的字符也当口令             | 明确通道顺序与位序，再通过解压及 CRC 判断口令边界                |
| RSA 与图片组合题   | 混淆 key1、key2 的来源，把看似十六进制的密钥文本做 Hex 解码 | 分别验证 RSA 因子与 PNG CRC，按附件代码规定的 UTF-8 编码拼接密钥 |

这四道题共同强调了数据表示和验证：同样一串字符，作为文本、原始字节或十六进制表示时含义不同。每完成一步，尽量用文件头、CRC、签名或加密往返验证结果，再进入下一阶段。

目前可以确认的完整 Flag 是 `flag{JS_Obfuscation_09181713}`。secret-read 的提交要求、紧急援助的后续消息构造，以及密径寻钥的最终 AES 解密，仍按原记录保留为待完成事项。
